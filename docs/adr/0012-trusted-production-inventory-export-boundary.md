# 可信生产库存出口边界

## 状态

已接受

## 决策

Civic 只把服务器确认的、绑定到 Registered Facility 的 Facility Accounting Interface 出口记录为生产库存消费。请求可以表达槽位、数量和出口类型，但物品 ID 与组件数据必须从服务器实际移出的 ItemStack 读取。出口记录和 FIFO 库存消费使用同一个 service/request 身份，并在 SQLite 中作为一组不可变审计事实持久化。

## 背景与权衡

Minecraft、Create 和物流模组没有一个跨模组且稳定的“销售完成”事件。扫描任意箱子、传送带或客户端提交的销售事实会把循环搬运、伪造身份和中间生产链重复计分带进国家实力。Civic 因此先提供一个明确的服务器权威出口边界；外部商店或公共工程适配器必须在真实出口完成后调用该边界。

这个选择可能漏掉没有适配器的真实交易，但漏算比把不可验证库存算成生产贡献更安全。Civic 不在出口记录中自动移动 LC 货币，正式付款仍由独立的财政状态机负责。

## 后果

- 出口事件可以用稳定 requestId 重放，重复重放不会再次移出物品或扣减年龄批次。
- 真实物品移出发生在 Minecraft 服务器线程，SQLite 记录在专用写线程；如果跨边界写入失败，系统宁可少算，也不能凭空增加贡献。
- 通用物流扫描、任意 Create 机器和外部销售模组仍需要各自的版本锁定适配器。
